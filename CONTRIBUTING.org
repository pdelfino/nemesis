#+TITLE: Contributing to Nemesis

Nemesis is developed on macOS first and mostly by Claude Code under the rules in =CLAUDE.md= and =SECURITY.org=. Humans follow the same rules.

* Toolchain

=make setup= then =make dev= runs the app from any state; =make gate= runs the gate and bare =make= lists the targets. The =Makefile= is a thin wrapper: it checks Node against =.nvmrc= (sourcing =~/.nvm/nvm.sh= itself, because Make runs =/bin/sh= where =nvm= is not loaded, and printing the =nvm use= command when the version is wrong), then calls the npm scripts below, which stay the single definition of each step. =make dev= runs the install first only when =node_modules/electron/dist= is missing.

- Node 24 LTS through nvm: =nvm use= reads =.nvmrc=.
- npm with the committed =package-lock.json=. Install with =npm ci --ignore-scripts= and then =node node_modules/electron/install.js=. Lifecycle scripts from dependencies are never run; Electron's binary download is the single explicit exception.
- No global tools are required beyond Make, which ships with the Xcode command line tools. Playwright downloads nothing extra for Electron.

** Seeing the window: =dev:debug= and =peek=

Claude Code builds the app without seeing it, so the development build can open a Chrome DevTools Protocol port and a script can look through it (#102):

- =npm run dev:debug= is =electron-vite dev= with =--remoteDebuggingPort 9222=. The port is a developer switch on loopback only: Chromium binds it to 127.0.0.1, electron-vite passes it only in development, and the packaged app never sets one.
- =npm run peek -- [--port 9222] [--out /tmp/peek.png]= attaches to that port with Playwright's =connectOverCDP= (=scripts/peek.mts=, no build step, no new dependency), prints an Org document on stdout with the window title, the mode line, one heading per visible buffer with its text (the CodeMirror documents included) and the palette state, then saves a PNG of the window. It launches nothing and sends no input; it only reads. When nothing listens it exits non-zero with one line on stderr. The end-to-end spec =tests/e2e/peek.spec.ts= runs the script against the built app on port 9333.

The same port serves the chrome-devtools MCP server for live inspection from a Claude Code session. It is added in local scope, so the repository carries no =.mcp.json= (a project server would be spawned by every headless queue run):

#+begin_src sh
claude mcp add --scope local chrome-devtools -- npx chrome-devtools-mcp@1.11.0 --browserUrl http://127.0.0.1:9222
#+end_src

** Notifications: macOS, phone and watch

When a session finishes its turn, needs a permission answer or an AskUserQuestion, or hits an error, the main process raises a notification (#90, =src/main/notify/=). The text is the session name, the moment, the elapsed time and the tool-call count, and nothing else: no prompt, reply, file path or page content. A click on the macOS notification brings the window forward on the pending request, or on the transcript.

The toggles live in the =notify= key of =settings.json=, or in the init file (#114, =docs/config.org=, "The notification toggles"). The Telegram pair is read from the environment once, at startup, and so are the four =NEMESIS_NOTIFY_*= toggles, which apply only while neither file has a =notify= key and are dropped in the next release:

| Variable                     | Values                       | Default                                        |
|------------------------------+------------------------------+------------------------------------------------|
| =NEMESIS_TELEGRAM_BOT_TOKEN= | the bot's token              | unset: no phone push                           |
| =NEMESIS_TELEGRAM_CHAT_ID=   | the chat the bot writes to   | unset: no phone push                           |
| =NEMESIS_NOTIFY_FINISHED=    | =always=, =unfocused=, =off= | =unfocused=: only when the window has no focus |
| =NEMESIS_NOTIFY_NEEDS_YOU=   | =on=, =off=                  | =on=                                           |
| =NEMESIS_NOTIFY_ERROR=       | =on=, =off=                  | =on=                                           |
| =NEMESIS_NOTIFY_SOUND=       | =on=, =off=                  | =off=                                          |

The phone push needs both Telegram variables; with one of them missing nothing is sent. Export them from your own shell profile or a file outside the repository, never from a file in it, and never paste the token into a transcript. Under test (=NODE_ENV=test=) the macOS sink is a spy the smoke reads and no push leaves the machine, whatever the shell exports. In =make dev= the notification shows under the Electron binary's identity; the packaged app needs its bundle identifier and signing (M5).

The Garmin watch needs no Garmin API: Garmin Connect mirrors the iPhone's notifications. In the Garmin Connect app, open the watch's settings, then Notifications and Alerts, then Smart Notifications, and allow Telegram (Apps, Telegram on). The iPhone's own Settings, Notifications, Telegram must allow notifications too, or there is nothing to mirror.

* The MCP door

The MCP server over the command table (#28) lives in =src/main/mcp/=: =catalog.ts= is the table of tools as data, =server.ts= relays each to the registry, the buffers, the prompter, the session manager or the transcript search, and =socket.ts= is the door. The door is =mcp.sock= in =app.getPath('userData')=, mode 0600, with =mcp.token= beside it, 32 random bytes as hex, mode 0600, new on every launch; both are removed at =will-quit=, and a stale socket from a crashed run is probed and removed at start. A connection whose first line is not =NEMESIS-MCP 1 <token>= is closed within a second with nothing sent. =bin/nemesis-mcp= is the client's side: it reads the token and forwards stdio, and holds no logic. Every tool has a confirmation class the door enforces: =free= answers at once, =yes= asks in the prompt buffer once per call with the client's name in the question, and =never= is refused. =cockpit_run_command= takes the class the command declares in its =mcp= field, =yes= when it declares none. The cockpit's own session gets the same catalog in process, minus =cockpit_send_prompt=, and its calls are asked by the permission bridge instead. Nothing in =src/shared/=, the preload or the renderer names the socket, the token or the folder; =tests/e2e/security/mcp-socket.spec.ts= holds that line.

* The gate

=npm run gate= runs the dependency script check (=scripts/check-deps.mjs=, SECURITY.org T5), typecheck, lint, unit tests, the end-to-end smoke and the security specs. It runs locally before every commit. GitHub Actions runs the same gate plus a secret scan and =npm audit= as a second opinion when a pull request is marked ready for review.

When an end-to-end or security spec goes red, the evidence is next to the result, not only in the assertion text. Every spec imports =test= and =expect= from =tests/e2e/_test.ts=, whose automatic fixture leaves two files in the test's folder under =test-results/= whenever a test ends in a status it was not expected to: =window-<n>.png=, the first window of the n-th app the test launched through =launchApp=, and =main.log=, everything the Electron main process wrote to stdout and stderr. Both are also attached to the Playwright report. The specs keep their own cleanup, so the frame is taken as =app.close()= begins, right after the assertion threw; a test that timed out still has its window open and gets a live screenshot. To prove the mechanism with one command, run the probe, which launches the app and fails on purpose (the run exits non-zero by design):

#+begin_src sh
ARTIFACT_PROBE=1 npx playwright test --project=app -g artifact-probe
ls test-results/*/window-1.png test-results/*/main.log
#+end_src

Without =ARTIFACT_PROBE=1= the probe is skipped, so the gate never sees it.

On GitHub, a red =gate= job uploads =test-results/= as the =test-results= artifact (kept 7 days): open the failed run, scroll to Artifacts at the bottom of the run summary and download it for the same =window-<n>.png= and =main.log= files. A green run uploads nothing.

Before a push that reaches GitHub, the workflow itself runs on this machine: =make ci= runs the =gate= job of =.github/workflows/ci.yml= with act on the host (=brew install act=), so a clean =npm ci=, the Electron binary, the gate and =npm audit= run exactly as the macOS runner would. Only a green local run is pushed, and a pull request stays a draft while work lands on it: the workflow skips drafts and runs on main, on tags and on a pull request marked ready for review (Pedro, 2026-OCTOBER-19, for cost). A race that shows only on GitHub's slower runner is reproduced here first, under load or with a trace, before it is fixed.

* Issues are the unit of work

Every issue that describes code carries =## Verify= (a terminating command or a named spec) and =## Do not touch= (the boundary). An issue with a real design choice carries an =## Approach= table of two or three options (files touched, cost, risk, what each rules out), one marked Recommended, and waits for the maintainer's pick before anyone edits code; nobody asks an open-ended "how do you want it". One-file fixes and errands skip this. Done means the checklist is resolved: tick, strike with a reason, or bold what remains, then a one-line "verified with ..." comment. A choice between libraries or architectures that a later issue would otherwise reopen is recorded as an ADR; the process, the numbering and the index live in =docs/adr/README.org=. An ADR lands as =proposed= with the Approach table and flips to =accepted= when the maintainer picks.

* Commits and pull requests

Interactive sessions commit straight to =main= after a green local gate; speed over ceremony is the maintainer's call. The unattended queue works on its own branch (=claude-queue/<number>= per issue, or the stack name of a =--stack= run) and opens a draft pull request, which is its review surface. Small commits with a Conventional Commits prefix. A commit or pull request names the issue, the Verify commands that were run, and any new dependency with its one-line justification.

Pull requests that touch =src/main/security/=, =src/preload/=, the permission bridge in =src/main/agent/=, =SECURITY.org= or =tests/e2e/security/= are reviewed interactively by the maintainer before merge, whoever authored them.

* Style

- Documentation in Org. Markdown only where a tool requires it.
- No em-dashes, in code comments included.
- Dates in prose with the month name, for example 2026-OCTOBER-17. Filenames and code stay ISO.
- Keybinding notation follows Emacs: =C-x C-s=, =M-x=.

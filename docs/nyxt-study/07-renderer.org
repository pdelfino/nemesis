A note on the sources the issue named. The =ffi-*= generics are not in
=renderer.lisp=, which is 19 lines and declares only the =renderer= class and
two generics (=install=, =uninstall=). They are declared in
=source/foreign-interface.lisp=, through the =define-ffi-generic= macro. The
issue also named a separate GTK WebKit file, which does not exist in
this checkout: the WebKit code lives in =source/renderer/gtk.lisp= (1823
lines) and the GObject helpers in =source/renderer/gi-gtk.lisp=. The checkout
also has =source/renderer/electron.lisp= (597 lines), a second implementation
of the same contract on Electron. That is the most useful file in this study:
it shows which methods Nyxt itself found it could and could not answer on
Electron. Every Lisp file cited below was checked to exist.

* The contract: how a renderer plugs in

** Three pieces

1. =renderer= (=source/renderer.lisp=) is a class with a =name=. An instance
   is bound to =*renderer*=. =install= and =uninstall= are the only two
   generics in that file. =install= in =source/renderer/electron.lisp= does
   one thing: it makes the renderer's classes (=electron-browser=,
   =electron-scheme=, =electron-window=, =electron-buffer=,
   =electron-download=) superclasses of the renderer-neutral placeholders
   (=renderer-browser=, =renderer-scheme=, =renderer-window=,
   =renderer-buffer=, =nyxt/mode/download:renderer-download=). So the core's
   =buffer= class inherits the foreign object slot and the methods from
   whichever renderer is installed, and the core never names WebKit or
   Electron.
2. =define-ffi-generic= (=source/foreign-interface.lisp=) declares a generic,
   exports it, and gives it a dummy default method that ignores its
   arguments when no method is supplied. With =:setter-p= it also defines a
   dummy =(setf name)=. The consequence is the rule of the whole design: an
   operation a renderer does not implement silently does nothing instead of
   failing. A core feature can call =ffi-buffer-add-user-script= on a
   renderer that has no such thing and nothing tells the caller.
3. Some generics carry a renderer-neutral method on the core classes, and
   the renderer method runs through =call-next-method=. The pattern, seen in
   =ffi-buffer-delete=, =ffi-buffer-load=, =ffi-window-set-buffer= and
   =ffi-window-active=, is: the core runs its hooks and bookkeeping
   (=buffer-delete-hook=, =buffer-load-hook=, =window-set-buffer-hook=,
   =last-active-window=), then the renderer does the foreign work. The hooks
   therefore fire identically on every renderer. =ffi-buffer-load= also
   handles the =javascript:= scheme in the core, by evaluating the decoded
   path, so a renderer never sees that scheme.

In =source/renderer/gtk.lisp= the macro =define-ffi-method= wraps a method
body so it runs on the GTK thread (=ffi-within-renderer-thread=, with a
channel when the caller is on another thread). That is the thread-affinity
problem of WebKit: every call into the foreign object must come from the
renderer's own thread. Electron has the same shape in a different form: the
Lisp side talks to a separate Node process by messages
(=electron::message= in =source/renderer/electron.lisp=), so every call is
asynchronous and the synchronous ones are built on top of a wait.

** What a renderer must also provide besides the generics

The generics are only the calls from core into renderer. The reverse channel
is the =on-signal-*= family, also in =source/foreign-interface.lisp=: the
renderer calls these when something happens, and the core method runs the
modes (=on-signal-notify-uri= runs each enabled mode's method first so modes
can alter the behaviour of the buffer). The pair is the whole interface:
commands down, events up.

* Every renderer method, grouped by concern

All names are in =source/foreign-interface.lisp=. The Electron column says
what =source/renderer/electron.lisp= did (done, stubbed with an error, or
left as a commented-out TODO). "Owner" is the Nemesis security baseline
module that already decides the concern; "none" means no module owns it yet
and the page-buffer API has to.

The two lines that matter. First, =ffi-buffer-initialize-foreign-object= is
where Nyxt's design and the baseline meet: whatever the renderer builds here
is the security surface, and on Electron that is the =webPreferences= object.
The baseline already froze it in =HARDENED_WEB_PREFERENCES= and checks it
back from the live contents. Second, the Electron renderer sizes a view by
hand (=update-active-buffer-bounds= subtracts the status and message buffer
heights from the window bounds). Nemesis lays out its own chrome in the
cockpit renderer, so it must decide the same thing once: who owns the page
view's rectangle (see the API at the end).

=on-signal-decide-policy= in =source/renderer/gtk.lisp= is the most
instructive method in the file. WebKit gives one callback that carries a
decision type (navigation, new window, response) and the method decodes the
request, mime type, headers, modifiers and mouse button into one record, then
hands the core a single yes, no or download answer. Electron splits the same
decision across several events and no single hook. Nemesis already has the
split halves in =navigation-policy.ts=; what it does not have is a
renderer-neutral record that the prompt buffer and the history can read.

Input is the place where a Nyxt-style cockpit and a browser disagree. In
Nyxt the core owns every keystroke because the keymap system is its own. On
Electron the page receives keys first, so the keyboard layer is only as good
as =before-input-event=. Nemesis cannot hand a key to the page and also own
it: the rule has to be decided per mode (an insert mode that forwards, a
normal mode that consumes), and it is the next study's subject (#14 and the
keymap ADR), not this one.

** Scripting

| Nyxt generic                                | What it does                                              | Electron equivalent                                                     | Nyxt on Electron | Owner |
|---------------------------------------------+-----------------------------------------------------------+-------------------------------------------------------------------------+------------------+-------|
| =ffi-buffer-evaluate-javascript=, =-async=  | run a JS string in the page, optional =world-name=        | =webContents.executeJavaScript(code)= (main world), =webFrame.executeJavaScriptInIsolatedWorld= from a preload for an isolated world | done; =world-name= ignored (TODO) | none; this is a hole in the baseline, see below |
| =ps-eval=, =define-parenscript=, =define-parenscript-async=, =ps-labels= (=source/renderer-script.lisp=) | compile Lisp to JS with Parenscript, run through the two generics above, return the value | a typed preload function exposed over =contextBridge=, called by IPC   | n/a (macro layer) | #53 (IPC sender and shape validation) |
| =ffi-buffer-get-document=                   | raw HTML of the page, read in 10000-character slices through script | =webContents.executeJavaScript('document.documentElement.outerHTML')=, or the accessibility tree for the semantic view | default method | none |
| =html-write=, =html-set=, =html-set-style=, =add-stylesheet= (=source/renderer-script.lisp=) | write HTML or CSS into a buffer from the core | not for pages; for internal pages only, from the cockpit's own renderer | n/a | #50 |
| =define-internal-page=, =internal-page= (=source/renderer-script.lisp=) | register an internal URL whose content the core generates, matched by URL | =protocol.handle('nemesis', ...)=                                    | done (scheme) | #50 |

=source/renderer-script.lisp= is not renderer code; it is a layer of
macros over exactly two generics. That is a good sign of how narrow the
renderer boundary is: all of Nyxt's page scripting (hints, search in page,
DOM reads, link following) flows through =ffi-buffer-evaluate-javascript= and
its async twin. It is also the baseline's gap. SECURITY.org has no row for
"the app runs script in a page". Nyxt's answer, evaluating a string in the
page's own world, would put app code and page code in the same JavaScript
world, which the baseline's page-content-is-data rule rules out. In Electron
the right shape is a preload on the page buffer that runs in an isolated
world and exposes a minimal, typed bridge; the main process never builds a
JS string out of page data. That is the one decision the first child issues
must make before any hint-mode work.

| =ffi-buffer-proxy= (setf-able)              | per-buffer proxy URL and ignored hosts                    | =session.setProxy()=: per session, not per buffer                       | stubbed, errors  | #54 (DNS over HTTPS off, WebRTC public interface only); proxy is none |

The sharpest contrast with the baseline is =process-permission-request=. It
builds a question per request type and grants on a yes. The Nemesis baseline
reaches the same ask, but starts from deny, keeps the allow set in memory so
it dies with the process, and keys it on scheme plus host (=originOf= in
=src/main/security/permissions.ts=), never on a path. The renderer contract
needs nothing from this concern: permissions are session policy, installed
once, and never a per-buffer call. The Nyxt shape of "a renderer method per
permission" is the wrong grain for Electron.

** Downloads

| Nyxt generic                                | What it does                                              | Electron equivalent                                                     | Nyxt on Electron | Owner |
|---------------------------------------------+-----------------------------------------------------------+-------------------------------------------------------------------------+------------------+-------|
| =ffi-buffer-download=                       | start a download of a URL through a buffer's web view     | =webContents.downloadURL(url)=                                          | done             | #51 (=downloads.ts=: the page-offered item is refused at =will-download=; the app requests the URL itself after a yes) |

Nyxt lets a page start a download and then manages it; Nemesis does the
opposite, and that is deliberate (SECURITY.org T2). So of the whole download
concern the renderer contract needs one method, "ask the page buffer to
download this URL that the user confirmed", and the rest stays inside #51.

** Printing

There is no print generic. =ffi-print-status= and =ffi-print-message= in
=source/foreign-interface.lisp= are misleadingly named: they print into the
status buffer and the message buffer (the Nyxt equivalent of a modeline and
an echo area), by writing HTML to a buffer through =html-write=. Neither
prints a page. Nyxt has no page printing on either renderer. Electron has
=webContents.print()= and =webContents.printToPDF()= when it is wanted; no
module owns it. It is not wanted in the first milestone (see the end).

** Zoom

| Nyxt generic                                | What it does                                              | Electron equivalent                                                     | Nyxt on Electron | Owner |
|---------------------------------------------+-----------------------------------------------------------+-------------------------------------------------------------------------+------------------+-------|
| =ffi-buffer-zoom-ratio= (setf-able)         | read and set the zoom ratio; default method sets =document.body.style.zoom= by script and an =:after= method stores it in the buffer's =zoom-ratio= slot | =webContents.getZoomFactor()=, =setZoomFactor()=                        | done (positive floats only) | none |

The default method is the useful design lesson: a renderer without native
zoom still works because the core falls back to a script. Electron has native
zoom, so the fallback is dead code for Nemesis. Note that Electron's zoom is
remembered per origin by Chromium unless the factor is set again on
navigation; the page buffer has to say which behaviour it wants.

matches the baseline: a page buffer's preferences are an immutable frozen
object, never relaxed at runtime.

* The page-buffer API Nemesis needs first (M4's first child issues)

Narrower than Nyxt's. Nyxt's contract is about sixty-five generics because it had
to cover two toolkits and kept every WebKit setting reachable. Nemesis has
one engine, and the baseline has already fixed most of what Nyxt left to the
renderer. Names are proposals for the issue writer, in TypeScript style, in
=src/main/page-buffer.ts= beside =buffers.ts=.

1. *Create and destroy.* =createPage(spec)= builds a =WebContentsView= with
   =HARDENED_WEB_PREFERENCES=, the partition chosen from the spec
   (=persist:default= or =ephemeral=), and runs =applyNavigationPolicy(contents,
   'page')= before the first load. =destroyPage(id)= closes the contents and
   removes the view. Two specs: the live preferences read back hardened with a
   page buffer open (the M4 acceptance in #73), and a destroyed page leaves no
   listener behind. Maps to =ffi-buffer-initialize-foreign-object= and
   =ffi-buffer-delete=.
2. *Load and move.* =load(id, url)=, =reload(id)=, =back(id)=, =forward(id)=,
   all through =navigationAllowed('page', url)=; a refusal is a notice, not a
   throw. Maps to =ffi-buffer-load=, =-reload=, =-navigate-backwards=,
   =-navigate-forwards=. The core-side hook (Nyxt's =buffer-load-hook=) is a
   cockpit hook point, to be named by the hooks ADR (#16, ADR 0005).
3. *State up.* One event stream, validated at the IPC boundary (#53): URL
   changed, title changed, loading started, committed, finished, failed with
   a reason, redirect. Maps to the =on-signal-*= family collapsed to one
   discriminated union in =src/shared/buffers.ts=. The URL shown is the
   committed top-frame URL (SECURITY.org T3).
4. *Layout.* One owner for the page view's rectangle. The cockpit renderer
   reports the rectangle it wants (=setBounds(id, rect)=); the main process
   applies it. This is what the Electron renderer in Nyxt does by hand
   (=update-active-buffer-bounds=), and the thing to get right once.
5. *Focus and keys.* =focus(id)= and a =before-input-event= listener that
   asks the keymap layer, per mode, whether the key is consumed or forwarded.
   Maps to =ffi-focus-buffer=, =ffi-focused-p= and the key signals.
6. *Zoom.* =zoom(id)= and =setZoom(id, factor)=, with the per-origin
   behaviour stated in the issue. Maps to =ffi-buffer-zoom-ratio=.
7. *Page script, behind one narrow door.* A preload on page buffers, isolated
   world, one typed bridge for the semantic view and hint mode (#73 items),
   no =executeJavaScript= built from a string that includes page data. Maps to
   =ffi-buffer-evaluate-javascript=, deliberately not as a general eval.
   Needs a SECURITY.org row and a spec before it ships, and Pedro's review as
   anything under =src/preload/=.
8. *Download request.* =requestDownload(id, url)= calling the one path in
   #51; no renderer-side download management.

Items 1 to 3 are the first child issues; 4 and 5 follow in the same
milestone; 6 and 8 are small; 7 is the one that needs an ADR first.

* What is deliberately not wanted

- *A renderer interface with a dummy default.* The =define-ffi-generic= rule
  that an unimplemented operation silently does nothing is right for a
  project with two toolkits and wrong for one engine. The Nemesis page buffer
  is a concrete class; an operation that is not supported fails loudly or is
  absent from the type.
- *A second renderer.* Nothing in M4 abstracts over WebKit or another engine.
  The seam stays where Electron puts it (=webContents=, =session=,
  =WebContentsView=, =protocol=), and the type is the interface.
- *=ffi-within-renderer-thread=.* Main owns every =webContents= on one thread.
- *Per-buffer proxy, cookie-policy enum, JavaScript/WebGL/image toggles.*
  Electron cannot change them on a live view, Nyxt's own Electron renderer
  stubs them, and the baseline fixes the preferences. Per-origin settings come
  later, as a recreate-the-view operation if ever.
- *User scripts and user styles in M4.* Arbitrary code in visited pages is a
  security decision (a new row in SECURITY.org, a spec, Pedro's review), not a
  convenience method.
- *Page printing.* Nyxt has none; Electron makes it easy; nothing in the plan
  asks for it.
- *Parenscript-style compile-to-JS from the core.* Nemesis has no Lisp. Page
  interaction goes through a typed preload bridge, never a string assembled in
  main.
- *The decide-policy mega-callback.* The record is useful (kept as the
  navigation notice the prompt buffer reads), the single hook is not: the
  baseline's split guards stay split.
- *A permission method per request type on the renderer.* Permissions are

#+TITLE: The config file
#+OPTIONS: toc:nil

Nemesis reads one file of your code at start and again on =M-x reload-config=,
the way Emacs reads =init.el=. The design is ADR 0006
([[file:adr/0006-config.org][docs/adr/0006-config.org]]); this page is how to use it. Landed in #71.

* Trust

*The config is trusted code with the app's privileges.* It runs in the main
process, as you, like =init.el= runs in Emacs. The loader hands the file one
object, =nemesis=, and nothing else is in scope, but =node:vm= is not a
security boundary and Nemesis claims no sandbox: put nothing in the file you
would not run in a terminal. The file never runs in the renderer or in a
page, and no IPC channel loads or evaluates it.

* Where it lives

- =~/.config/nemesis/init.ts=, the user's, not the profile's: keep it in your
  dotfiles. The app writes it only when you run =journal-promote= (see Eval),
  and then only appends to its end.
- =settings.json= stays in the profile's =userData= folder and loads first;
  the init file overrides its values in memory and writes nothing back.
- Start with =--no-config= to skip the file (the safe mode).
- A missing file is silent. Under test (=NODE_ENV=test=) the folder named by
  =NEMESIS_CONFIG_DIR= stands in for =~/.config/nemesis=, and no folder means
  no config.

* The language

One file in the erasable subset of TypeScript, the subset Node strips without
a compiler: interfaces, type aliases, annotations, =import type=, =as=,
=satisfies=. No =enum=, no =namespace=, no constructor parameter property, no
decorator. There is no runtime =import= and no =require=; =import type= is
erased before the file runs. Types are replaced by whitespace, so a line and
column in an error are the line and column in your file.

* What =nemesis= offers

| Member                                      | What it does                                                                                          |
|---------------------------------------------+-------------------------------------------------------------------------------------------------------|
| =nemesis.defineCommand({ name, doc, run })= | A command, as the cockpit's are: a kebab-case name, a doc line for the palette, a body. M-x finds it. |
| =nemesis.defineKeymap('user', spec)=        | Bindings in the =user= layer, chord to command name, in Emacs notation (ADR 0002).                    |
| =nemesis.bindKey(chord, command)=           | One binding in the =user= layer.                                                                      |
| =nemesis.settings.set(key, value)=          | Overrides a =settings.json= key for this run, checked by the same rules.                              |
| =nemesis.settings.get(key)=                 | The value in force for this load.                                                                     |
| =nemesis.buffers.list()=                    | The open buffers: id, kind, title.                                                                    |
| =nemesis.commands.run(name)=                | Runs a command by name, once the cockpit is up.                                                       |
| =nemesis.notice(text)=                      | A notice in the transcript, recorded in the session folder.                                           |
| =nemesis.on(point, { name, doc, run })=     | A handler at a hook point (ADR 0005), with the source =config=. See Hooks below.                      |
| =nemesis.off(point, name)=                  | Removes a handler by point and name.                                                                  |

The =user= layer sits above the global map and below the per-buffer maps, so
a chord there wins over the cockpit's global one. A config command cannot take
a cockpit command's name: to change what a key does, bind it to a new name.
=nemesis.defineMode= arrives with ADR 0004's mode registry (ADR 0006, step 3).

** The notification toggles

The =notify= key of =settings.json= (#114) holds the notification toggles of
#90, each =true= or =false=; an absent toggle takes the default below.

| Toggle                      | Default | What it does                                          |
|-----------------------------+---------+-------------------------------------------------------|
| =finished=                  | =true=  | A notification when a turn ends well                  |
| =finishedOnlyWhenUnfocused= | =true=  | With =finished= on: only when the window has no focus |
| =needsYou=                  | =true=  | A permission request or a question                    |
| =error=                     | =true=  | A turn or a stream that ended in an error             |
| =sound=                     | =false= | The system sound with the notification                |

#+begin_src json
{
  "notify": { "finished": true, "finishedOnlyWhenUnfocused": false, "sound": true }
}
#+end_src

The init file sets one toggle at a time with a dotted key, over the object in
force: =nemesis.settings.set('notify.finished', false)=; =notify.loud= is an
unknown setting, and =nemesis.settings.get('notify.finished')= is =null= while
neither file has a =notify= key. The toggles are read at every notification, so
a reload applies them to the next one.

Without a =notify= key in =settings.json= or the init file, the
=NEMESIS_NOTIFY_*= environment variables of CONTRIBUTING.org still decide, for
this release only; the next one drops them. The Telegram bot token is a secret
and is never a setting: it stays in =NEMESIS_TELEGRAM_BOT_TOKEN=, with its chat
id beside it in =NEMESIS_TELEGRAM_CHAT_ID=.

* A worked example

#+begin_src typescript
// ~/.config/nemesis/init.ts
// Trusted code: this file runs in the main process with the app's
// privileges, like init.el. Erasable TypeScript, no runtime imports.

// One setting: pin the appearance instead of following the OS. Checked
// like settings.json would be; a typo in the key is an error with a line.
nemesis.settings.set('theme', 'dark')

// One command, the shape of src/main/commands/registry.ts: a kebab-case
// name, a doc line the palette shows, a body.
nemesis.defineCommand({
  name: 'count-buffers',
  doc: 'Says how many buffers are open.',
  run(): void {
    nemesis.notice(`${nemesis.buffers.list().length} buffers open`)
  },
})

// One keymap, the shape of ADR 0002: the user layer sits above the global
// map, so C-s now searches every transcript and C-x s searches this buffer,
// the reverse of the cockpit's defaults; the new command gets a key too.
nemesis.defineKeymap('user', {
  'C-s': 'search-transcripts',
  'C-x s': 'search-buffer',
  'C-c n': 'count-buffers',
})
#+end_src

* Hooks

A hook is a declared point the cockpit fires, and a handler is a named
function the config registers there (ADR 0005, #165). There is no advice:
nothing wraps a command, a handler runs only where its point fires.

| Point             | Kind        | Fires                                    | The event                                        |
|-------------------+-------------+------------------------------------------+--------------------------------------------------|
| =after-init=      | observer    | once, when the first window is up        | =commands= (names), =buffers=                    |
| =buffer-created=  | observer    | a buffer opened                          | =buffer=                                         |
| =buffer-switched= | observer    | the current buffer changed               | =from= (or =null=), =to=                         |
| =buffer-killed=   | observer    | a buffer killed                          | =buffer=                                         |
| =before-command=  | interceptor | before a command runs, from any caller   | =command=, =context=                             |
| =after-command=   | observer    | after it ran; not when a hook refused it | =command=, =context=, =ok=, =durationMs=         |
| =session-started= | observer    | a session's first frame                  | =sessionId=, =model=, =permissionMode=           |
| =turn-ended=      | observer    | a turn ended                             | =sessionId=, =isError=, =durationMs=, =numTurns= |
| =before-quit=     | observer    | the app is quitting                      | nothing                                          |

An event holds names, ids, counts and buffer records, never prompt text,
assistant text, tool input or page content.

#+begin_src typescript
// Say which buffer was just made. The name is kebab-case, like a command's:
// it is what list-hooks shows, what a failure notice names, and what
// nemesis.off and remove-hook take.
nemesis.on('buffer-created', {
  name: 'say-created',
  doc: 'Says which buffer was made.',
  run(event): void {
    nemesis.notice(`created ${event.buffer.title} (${event.buffer.kind})`)
  },
})

// The one interceptor: return { veto: true, reason } and the command does
// not run; the reason is a notice in the transcript.
nemesis.on('before-command', {
  name: 'keep-the-transcript',
  doc: 'Refuses kill-buffer while the transcript is the current buffer.',
  run(event) {
    if (event.command === 'kill-buffer' && event.context.bufferType === 'transcript') {
      return { veto: true, reason: 'the transcript stays open' }
    }
    return undefined
  },
})
#+end_src

The rules:

- Handlers of a point run oldest first: the cockpit's, then a mode's, then the
  config's, each in the order =on= was called.
- A handler may be =async=; each is awaited, two seconds at most for an
  observer, thirty for =before-command=. The second argument is an
  =AbortSignal= aborted at that limit. An observer past it is reported and
  left behind; an interceptor past it refuses the command.
- A handler that throws is reported in a notice with its point, name and
  source, and the next one runs. It stays registered, so the notice comes
  back until the file is fixed. A throw in =before-command= refuses nothing.
- A point fired from inside one of its own handlers (a =before-command=
  handler that runs a command) runs no handler the second time, and says so.
- A second handler of the same name on a point is an error on the file's
  line, as a misspelt point or a name that is not kebab-case is.
- =reload-config= drops every =config= handler and registers the file's
  again, so a handler runs once per event, however many reloads.
- =M-x list-hooks= shows every handler in the help buffer, by point, with its
  source; =M-x remove-hook= removes one chosen in the palette until the next
  reload. =nemesis.on= and =nemesis.off= belong in the file: eval refuses them.

* Reload

=M-x reload-config= runs the file again. A load is staged and committed whole:
everything the file asks for is checked first (a name that is not
kebab-case, a chord that does not parse, a binding to a command that does not
exist, an unknown setting), and only a load that runs to its end replaces the
previous one. On success the previous load's commands and bindings are
dropped, the new ones registered, the palette and the menu bar follow, and
one line in the transcript gives the counts. =theme= applies at once,
=model= on the next session, =verify= on the next check and
=searchEngines= on the next =open-url=; =stopGateRetries= applies at the next
gated turn end, =fanOutMax= (1 to 30, 5 by default, #160) at the next
=fan-out=, =notify= at the next notification and =restore= at the
next quit (#127: off, no window is saved or reopened; a start with
=--no-restore= skips the reopening once), and =hints= at the next =f= in a
page buffer (#123: =hints.alphabet=, two or more distinct lowercase letters
or digits, the home row =asdfghjkl= by default, and =hints.maxLength=, the
longest label, 1 to 6, 3 by default); =sessionsDir=
and =keyscheme= are read once at start, and the line names them when they
need a restart. A top-level loop is stopped after two seconds.

* Errors

A syntax error, an error the file throws, or a name the API rejects opens the
help buffer under =Config errors= with the file, the line, the column when
there is one, and the message, and a notice says the same in the transcript.
Nothing from that load is applied: the previous config stays live, or the
defaults on a first load, and the app keeps running. The environment panel
(=C-c C-e=) lists the file as loaded with its counts, as an error with its
line, or as absent; =RET= on it opens the file after a yes.

* Eval and the journal

=M-x eval-expression= reads one form of erasable TypeScript and evaluates it
in the main process with the same =nemesis= object the file gets, and nothing
else in scope; the value is a notice in the transcript. =M-x repl= opens the
=*repl*= buffer, where =RET= reads a form and the form and its value are
added to the buffer. Every form shares one =node:vm= context for the life of
the app, so a =const= one form declares, the next one reads. A form is one
line of at most 200 characters, read through the palette. Landed in #72.

A form that defines or redefines a command or a binding takes effect at once:
the command is in M-x, the key runs it. It may redefine a command of the file
or of an earlier eval, never one of the cockpit's. =nemesis.settings.set= is
refused at eval: settings belong in the file. A reload keeps what eval
defined, except where the file now defines the same command or binds the same
chord, which wins.

Every such form is appended to =journal.org= beside =init.ts=, an Org file
with one heading per entry, its timestamp and what it defined, and the form in
a source block. The mode line shows =journal: N= while N entries wait.
=M-x journal-promote= picks an entry and appends its form to the end of
=init.ts= with a comment naming where it came from, then drops it from the
journal; =M-x reload-config= loads it from the file. =M-x journal-discard=
deletes an entry; what it defined stays live until a restart. Under
=--no-config= eval still works and nothing is journaled, and the note after
each definition says so.

Eval runs only on a command you ran from the cockpit's keys or palette. No
page buffer and no MCP server reaches it. Like the file, it is trusted code
with the app's privileges.
